# План измерения

## Единица анализа

Один пользователь-владелец на первый показ функции создания семейной группы. В тестовом наборе `user_id` — искусственный идентификатор. Повторные показы не создают новые строки в `exposures`. Воронка приглашённых участников измеряется отдельно и здесь не реализована.

## События

| Событие / таблица | Момент фиксации | Обязательные поля |
|---|---|---|
| `exposures` | Первый успешный показ функции пользователю | user_id, exposed_at |
| `family_created` | Сервер подтвердил создание группы | event_id, user_id, event_name, occurred_at |
| `limit_set` | Сервер подтвердил сохранение валидного лимита | те же |
| `report_viewed` | Отчёт успешно загружен и показан | те же |
| `budget_opened` | Пользователь открыл модуль бюджета | те же |

Для реального внедрения нужны дополнительные атрибуты: версия схемы, платформа, версия приложения, время приёма события, обезличенный family_id и версия настройки лимита. Они не выдумываются в демонстрационном наборе. Суммы, категории и имена родственников для этих метрик не нужны.

## Определения

**Активация за 7 суток.** Пользователь последовательно создал группу, установил лимит и открыл отчёт в полуоткрытом интервале [первый показ; первый показ + 7 суток). Все шаги должны быть не раньше предыдущего. Для расчёта используется первый подходящий шаг после предыдущего; более ранние ошибочные события пропускаются. Равные timestamps допускаются из-за секундной точности источника; для строгого разрешения порядка потребовался бы серверный sequence ID.

Знаменатель — все показанные пользователи с полностью наблюдаемыми 7 сутками. Числитель — активированные среди них. Нельзя считать только тех, кто успел активироваться, и исключать остальных молодых пользователей выборочно.

**D14 retention.** Среди активированных пользователей, для которых полностью завершился календарный день D14, доля открывших бюджет хотя бы один раз в этот день. D0 — календарная дата активации в UTC. Например, активация 1 января в 23:50: D14 — весь день 15 января, а включение в расчёт возможно с 16 января 00:00 UTC. Это не скользящие 336–360 часов и не возврат в любой из первых 14 дней.

**Срез.** `as_of` — исключительная верхняя граница. События с occurred_at >= as_of не используются. Текущая демонстрация — пересчёт по времени совершения событий; она не восстанавливает историческое состояние хранилища до прихода запоздавших событий, потому что received_at отсутствует.

## Качество данных

- Одинаковый event_id с одинаковыми полями: повторная доставка, удаляется в SQL.
- Один event_id с разными полями: ошибка входных данных, расчёт останавливается.
- Неизвестный пользователь, событие или неканоническая дата: ошибка.
- Несозревшая когорта и пустой знаменатель: результат отсутствует; не заменяется нулём.
- События до первого показа и шаги вне окна не создают активацию.

Логи не доказывают соответствие продукта требованиям: приёмочные проверки функциональности описаны отдельно. Рост метрик не оценивается, контрольной группы нет. Генератор задаёт вероятности переходов искусственно, поэтому конверсии демонстрационного набора не подходят для продуктовых решений.

## Следующее исследование

На реальном пилоте проверить долю потерянных событий и сверку клиентских событий с сервером. Затем исследовать, связано ли выбранное определение активации с дальнейшим использованием. Для оценки эффекта новой функции заранее определить единицу рандомизации (семья), основную метрику, защитные метрики и размер выборки. Участники одной семьи не должны попадать в разные варианты.

Техническая справка: [SQLite: функции даты и времени](https://www.sqlite.org/lang_datefunc.html). SQL-файл и граничные тесты являются исполняемой спецификацией расчёта.

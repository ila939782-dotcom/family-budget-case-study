# Спецификация MVP

Автор: Илья Бочаров · School 21. Статус: учебная спецификация, не реализованная система.

## Проблема и ожидаемая ценность

Члены семьи видят отдельные расходы, но не всегда понимают остаток общего бюджета. Пользователь должен настроить лимит категории и увидеть текущую долю его использования. Предполагаемая ценность — более удобный контроль трат; снижение расходов или семейных конфликтов не доказано.

## Роли и границы

Владелец создаёт группу, приглашает участников, управляет составом и лимитами. Участник видит доступный ему семейный отчёт и добавляет свои расходы. Изменять роли и лимиты может только владелец. Участие требует явного принятия приглашения. Продукт не предоставляет доступ к чужому банковскому счёту и не выполняет платежи.

Первый пилот использует ручной ввод расходов и тестовую интеграцию. Автоматический импорт банковских транзакций — отдельная зависимость, не включённая в готовность MVP. Валюта одного бюджета — RUB. Все изменения расходов и лимитов фиксируются с автором и временем.

## Основной сценарий

```mermaid
flowchart LR
    A[Первый показ функции] --> B[Создание семейной группы]
    B --> C[Лимит категории]
    C --> D[Сводный отчёт]
    D --> E[Возврат к бюджету]
```

Владелец открывает категорию «Продукты», устанавливает месячный лимит, сохраняет его и видит расходы, лимит и процент использования. Уведомления отправляются при достижении 80% и 100%. Эти пороги выбраны для единой версии спецификации; исходный прототип с порогом 90% не считается текущим контрактом поведения.

## Требования и приёмка

| ID | Требование | Проверка |
|---|---|---|
| FB-01 | Создание группы владельцем | Повтор запроса с тем же ключом идемпотентности не создаёт вторую группу |
| FB-02 | Принятие приглашения | До принятия пользователь не видит данные группы; отозванное приглашение не работает |
| FB-03 | Лимит категории | Значение строго больше нуля, точность до копеек; пустой ввод и отрицательные значения отклоняются |
| FB-04 | Изменение лимита | Участник получает отказ; владелец видит новое значение после сохранения; запись аудита сохраняется |
| FB-05 | Расчёт расхода | Суммируются подтверждённые расходы текущего календарного месяца группы; возврат уменьшает расход; повторы транзакции не учитываются |
| FB-06 | Уведомление | Одно уведомление на сочетание группа–категория–месяц–порог; повтор доставки события не вызывает новый push |
| FB-07 | Пересечение порога | Скачок с 70% до 105% вызывает одно уведомление о 100%; уведомление 80% отдельно не отправляется |
| FB-08 | Пересмотр лимита | Если снижение лимита пересекает порог, применяется та же логика дедупликации; уже отправленные пороги не сбрасываются |
| FB-09 | Отчёт | Сумма категорий совпадает с общим расходом при одинаковом наборе операций и периоде; отсутствие данных отображается явно |
| FB-10 | Выход из группы | Доступ прекращается немедленно; политика хранения ранее внесённых данных согласуется до пилота |

Деньги хранятся целыми копейками. Календарный месяц бюджета определяется сохранённой временной зоной группы. Время событий аналитики хранится в UTC. Политика валют, возвратов, прав доступа и хранения данных должна быть согласована владельцем продукта до реализации.

## За пределами MVP

Совместные накопительные цели, AI-рекомендации, веб-клиент, мультивалютность, автоматическое кредитование и перевод денег. Кейс не заявляет реализацию API, мобильного приложения, отправки push или банковских интеграций. SQL проверяет только спецификацию аналитики.
